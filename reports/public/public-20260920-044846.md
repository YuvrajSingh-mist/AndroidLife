### Limitations

- **Coverage is 14 / 60** (battery death at the end of day 1). HC set is **2 / 7**, ASK USER is **1 / 11** (and that one aborted at
  preflight), and days 2–3 were never touched. The comparable 60-denom therefore penalises **46 unreached tasks**.
- **No live ADB corroboration *at audit time*.** The phone was off with a dead battery, so this is the **first audit in the series
  written without on-device re-verification**; every end-state claim rests on the in-run `ui_states`, which are captured by the
  harness at action time and are the strongest available evidence — but a corrupted write after capture would not be caught.
  **Follow-up (2026-09-20, phone back online):** the device was re-checked directly and the calendar findings *were* revised as a
  result — see the next bullet, where the sync-revert explanation was disproven by direct measurement. The reset gate now also
  re-reads every write it makes.
- **`easy__calendar__002` — the seed was misplaced by one day (task vacuous, not a model failure). 🔄 RESOLVED BY RE-RUN 2026-09-21.**
  *(Re-run 2026-09-21 on a same-day `--apply` seed that was verified to sit on **Tue 22 Sep** **and** to render in the Calendar
  app — see the app-visibility note below. It **PASSED non-vacuously**: the model reported the real 14:30–15:00 overlap.
  The analysis below documents the original 2026-09-20 defect and is retained for the record.)*
  The task asks about
  **tomorrow afternoon**; `reset_phone.py` seeds `Team Sync` 14:00–15:00 and `Mentor 1 on 1` 14:30–15:30 at `offset_days: 1`.
  At run time both sat on **the run day itself** (Sun 20 Sep), leaving **tomorrow (Mon 21 Sep) with a single afternoon event**, so
  the task tested nothing. Consistency check: `Weekly Sync` 07:00 (Monday anchor) and `Gym` 06:30 (Tuesday anchor) were
  **correct**, while **every `offset_days` seed** (both `Weekly Sync` 10:00 copies + both conflict events) sat exactly
  **one day early**.
  **Mechanism: CONFIRMED — the last `--apply` ran on Sat 19 Sep, not on the run day.**
  `easy__calendar__002`'s own week view (`ui_states/0001.json`, captured at 09:30 on the run day) reconstructs the device
  calendar exactly:

  | Day | Events the agent saw |
  | --- | --- |
  | **Sun 20 Sep** (the run day) | `Weekly Sync` 10:00 · **`Team Sync` 14:00** · **`Mentor 1 on 1` 14:30** · `Weekly_Standup` 14:30 |
  | **Mon 21 Sep** ("tomorrow") | `Weekly Sync` 07:00 · `Weekly Sync` 10:00 · `Weekly_Standup` 14:30 |
  | Tue 22 Sep | `Gym` 06:30 |

  Every `offset_days` seed sits **exactly one day early** (the `offset_days: 1` copies on the run day, the `offset_days: 2`
  copy on D+1), while every `weekday` anchor (`Weekly Sync` Monday 07:00, `Gym` Tuesday 06:30) is **correct**. That is the
  signature of anchors computed on **19 Sep** — `19 Sep + 1 day = 20 Sep`. It is exactly the failure recorded in the
  `public_v2` comment (2026-09-16: seeded 15 Sep, batch started 16 Sep 01:13), and `weekday` anchors mask it because on
  consecutive days "next Monday" resolves to the same date. **The rule is therefore confirmed, not merely assumed: re-run
  `--apply` on the run day.**

  An earlier draft of this report blamed a **Google-sync revert** and prescribed "bump the dirty flag". That is **disproven**:
  the CalendarProvider **rejects** a `dirty` bind outright (`IllegalArgumentException: Only sync adapters may write to dirty`)
  and it fails **silently** (`content insert`/`update` still exit 0 through `adb shell`), while a plain write already sets
  `dirty=1` by itself. Binding it broke every calendar write instead of fixing anything. Likewise the claim that a gate
  "reported both on 2026-09-21 14:00 / 14:30 a few hours before launch" cannot be right — `verify_calendar_anchors` was
  committed at **16:23 on 20 Sep**, ~11 h *after* the run began, so it never ran that morning.

  **Root cause:** `--apply` was last run on **19 Sep**, so it was never applied for the run day.

- **A stale recurring run artifact polluted the calendar (seed hygiene).** `Weekly_Standup` (`_id=4378`) carries
  `rrule=FREQ=DAILY;COUNT=14;WKST=MO` from a `dtstart` of **Thu 17 Sep 14:30** — i.e. a **daily** 14:30–15:30 event spanning
  17–30 Sep, created by the **2026-09-17 gemma run's** agent and **uploaded** (`dirty=0`), never cleaned on reset. It is why
  "tomorrow afternoon" showed a `Weekly_Standup` the agent latched onto, and it would have added a spurious third afternoon
  event even had the seeds been correct. **Action:** reset must delete recurring run artifacts by title across the whole
  window, not just the exact-date rows.

  Because the anchors are day-relative, **any** run started without a same-day `--apply` will hollow out the other
  calendar-dependent tasks too (`hard__telegram-calendar__016`, `hard__drive-notes-telegram__010`).

- **🔴 NEW (2026-09-21): the anchor gate alone is not sufficient — the Calendar *app* must also show the seed.**
  Verifying the provider via `content query` proves the rows exist, but **not** that the app renders them. Measured on
  2026-09-21: the `Team Sync` / `Mentor 1 on 1` pair was present and **live** in the provider (`_id=4445/4446`,
  `calendar_id=16`) yet **did not appear in the Calendar app's Tuesday day view at all**, so a run would still have been
  vacuous while every DB-level gate said PASS. The app renders **server-derived** state for a synced Google calendar: a row
  with no `_sync_id` (never uploaded) is invisible, and a locally re-anchored row keeps rendering at its **old server date**.
  `adb` cannot upload calendar rows, so **seeding a synced calendar by `content insert` is fundamentally unreliable.**
  **Resolution used for this re-run:** the pair was created **once in the Calendar app UI** on the Google account
  (`yuvraj.mist@gmail.com`), which both uploads **and** renders; `reset_phone.py`'s `ensure_calendar_events` then detected
  them as exact-date matches and issued **no write** (verified: `present (synced=True)`, no duplicates, no sweep).
  **Remaining gap:** the seed gate checks the provider only — it cannot see this failure mode, and app-UI seeds are
  one-time events that go stale on the next run day. A durable fix (app-created **recurring** seeds, or a UI-level check in
  the gate) is still owed for `easy__calendar_002`.
- **`hard__youtube-settings__052` was partly pre-satisfied.** The DND schedule the agent “created” already existed as
  **`Rule 1 | 22:00-07:00`** — a leftover from the **16 Sep** run that was never cleaned. The agent's real contribution was
  correcting the end time to `08:00` and saving. The channel-notification half was done from scratch. This is a **seed-hygiene**
  issue: the DND rule should be deleted on reset, and the manual UI cleanup list must include it.
- **A leftover Notes entry was visible during the Maps task.** `medium-google-maps-002`'s Notes screen already contained a
  `Fastest route to Bhubaneswar Airport (… 13 km …)` note from a previous run before it created its own. It does not change the
  verdict (a new note was written), but the task's on-device state was not clean.
- **`medium__google-drive__001` is ungraded.** It has 10 tool calls, 10 `ui_states` and 10 screenshots but **no `output.json`**
  (ADB died mid-task), so no end state exists to judge. It is counted non-PASS, not FAIL.
- **The official `average_steps` figure is unusable for this run** (timed-out tasks write `steps: 0`). Any cross-model comparison
  on “steps” that includes this run must use the trajectory-derived **12.64**, not **3.86**.
- **`hard__telegram-calendar__016` is a model-protocol failure, not an app failure.** With **0 tool calls** it produced no
  evidence about Bonsai's Telegram, Calendar or KB behaviour at all — so this run cannot characterise the model on interaction
  tasks in either direction.
