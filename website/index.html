DailyBench500

28-Day Android Agent Benchmark

Evaluate whether a mobile agent can actually get things done on a real phone. DailyBench500 runs 530 everyday tasks across 31 apps over a fixed 28-day schedule, on a real Android device against a real LLM, and captures not just did it succeed but what doing it cost the phone: dollars, battery, heat, and steps.

  • Fixed 28-day schedule
  • 530 tasks · 31 apps
  • Easy / Medium / Hard
  • ASK USER + deterministic hard tasks
  • On-device battery & thermal capture
  • Cost tracked per LLM call

Problem Statement

Most agent benchmarks measure a model in a sandbox. The thing that made DailyBench500 different is the realization that the whole point of a phone agent is the phone. The agent lives in the same place people do, on devices with finite batteries, heat limits, and data caps.

So the benchmark asks a question most benchmarks skip: not just can the agent do the task? but what does doing it cost a real phone? A task completed in 40 steps with 3% battery and a cool phone is worth more than the same task in 180 steps that pushes the SoC into thermal throttle.

Vision

DailyBench500 is a protocol for measuring everyday agent usability, not just benchmark leaderboards. The goal is to test models of every size, including small models small enough to run on the phone itself, on tasks people actually do, so we learn whether an agent is genuinely useful to keep around, or only impressive in a demo.

Communication and cost matter too much to be reserved for the largest models.

Overview

DailyBench500 is a 28-day benchmark of 530 real-phone Android tasks. Instead of grading a model on a static screenshot, it runs an agent (via the mobilerun SDK) against a real device over ADB and measures:

  • Success: did the goal actually get achieved, verified against on-device state (not just the agent's claim).
  • Efficiency: how many steps and LLM calls did it take.
  • Cost: real USD per run, tracked through an LLM proxy per call.
  • Phone cost: battery drain (mAh, % delta), CPU/GPU/NPU/skin thermals, and charge-counter deltas captured per second on-device.

The benchmark covers three buckets of increasing difficulty:

  • Easy (216): single-app, 1 to 2 subgoal tasks worth 1 point each.
  • Medium (242): mostly cross-app (47%), 3 to 4 subgoals, worth 3 points.
  • Hard (72): 5+ subgoals, worth 5 points, split into 49 ASK USER (36 single-turn + 13 multi-turn KB, the agent must request load-bearing facts via the simulated user) and 23 DETERMINISTIC (fully verifiable on-device state).

Hard ASK USER tasks exercise the ask_user tool against a simulated user (gpt-5.4-mini), and hallucination controls catch agents that claim success on tasks whose data is deliberately absent.

Why vision mode trails. mobilerun is pixel-grounding only — it draws a labeled coordinate grid on the screenshot (10 divisions, x=N / y=N) but there is no OCR element-grouping, no element IDs, and no marked touch boxes. The model inspects the raw screenshot and eyeballs where to tap from pixels + grid, with no per-element anchors to lean on (that marked-boxes approach is UI-TARS / mobile-vlm / Mobile-Agent-v2, not mobilerun). So a vision run has to reconstruct every target from pixels alone — which is why vision consistently lands below the text runs below.

Benchmark Anatomy

Step 1
Task Prompt
DailyBench_530_v1.json task, placeholders resolved from tasks_vars
Step 2
MobileAgent on Device
mobilerun SDK drives the real phone over ADB (AndroidDriver / MobileAgent)
Step 3
LLM Inference
Real model over OpenAI-compatible endpoint (OpenRouter or local host), proxied per call for cost tracking
Step 4
Tool Calls + Telemetry
Every action on-device; battery/thermal sampled per second (samples.ndjson)
Step 5
Completion + Trajectory
output.json, trajectories/, run_metrics.json, Phoenix traces
Step 6
Aggregate Report
dailybench_report.py → MobileWorld-style metrics (SR, steps, UIQ)

Hard ASK USER tasks add a simulated-user round trip: the agent calls ask_user, and the simulated user (gpt-5.4-mini) answers with the hidden fact the task requires. A single skipped ask_user call fails the task.

Key Features

Benchmark Coverage

  • Fixed 28-day schedule: one-time shuffled, reused identically for every model for fair comparison.
  • 31 real apps: Telegram, Notes, Obsidian, Chrome, Calendar, Clock, Files, Gallery, Contacts, Maps, Drive, Gmail, YouTube, Settings, Calculator, Camera, Phone, Photos, Music, Messages, Google Search, Google Docs, Google Sheets, Google Slides, Google Meet, Weather, Swiggy, Prime Video, MakeMyTrip, BookMyShow, MSN News, Amazon Shopping.
  • 168 cross-app tasks (31.7%): multi-app chains that actually exercise app switching and data transfer.
  • 303 placeholder instances (119 distinct keys): contact, topic, time, amount, note title, song, route, city, etc., resolved per day at run time.

On-Device Measurement

Every task captures, per second, the true phone cost independent of the model under test:

  • Battery: dumpsys battery level delta %, charge-counter delta (µAh), per-app mAh.
  • Thermal: dumpsys thermalservice CPU, GPU, NPU, skin, and vendor phone temps, plus thermal status.
  • Cost: real USD per run through the LLM proxy (OpenRouter pricing or local host estimates).
  • Steps / tokens: step budget (50 default), LLM call count, prompt/completion tokens.

Evaluation Pipeline

Verified success. A task passes only when the goal is actually achieved on device, checked against on-device state, not the agent's complete() claim. Hallucination controls (tasks whose data is deliberately absent) catch false self-reported success: an honest failure is a pass; a hallucinated success is a fail.

Aggregation follows the MobileWorld metrics (arXiv:2512.19432): Success Rate (overall, per bucket, interaction vs GUI-only), Average Completion Steps, Average User Queries, and User Interaction Quality (UIQ), excluding the MCP metric. See the paper.

Technical Details

The harness is uv-managed end to end: the dataset lives in benchmarks/dailyBench-600/, the runner in dailybench_runner.py / dailybench_tasks.py, and run artifacts under assets/runs/ (with per-day Phoenix DBs in assets/db/dayN/). The website data file is generated directly from the dataset (see website/tools/build_site_data.mjs).

Tracing (Phoenix)

Every LLM call, tool execution, and agent step is captured as OpenTelemetry spans by Arize Phoenix (uv run phoenix serve --port 6006), giving a full trace tree per task at localhost:6006.

Reference Device

  • OnePlus CPH2423 (Android 15, non-rooted), wired or wireless ADB.
  • Host-side scrcpy --record for video artifacts (off by default to save disk).
  • Model host: any OpenAI-compatible endpoint, OpenRouter or a local model server.

Benchmark Summary

The public benchmark is a 60-task, 3-day preview drawn from the 530-task corpus (every task keeps its real 530 task_id, exact prompt text, and placeholder slots) so the pipeline, seeds, and grading can be exercised on a small, self-contained sample. Its bucket, app, and difficulty distributions intentionally track the parent corpus. See How it was formed for the full story, and Tasks for the 530-task corpus.
