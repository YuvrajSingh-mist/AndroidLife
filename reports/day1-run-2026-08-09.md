### False pass: the pizza task (`medium__gallery__001`)

Reported `success=true` ("searched for pizza photos, selected best 3 by
resolution, saved to *Best Pizza Photos*"), but the trajectory + screenshots show
the agent **saved three random user photos, not pizza**:

- The model searched "pizza" in Google Photos, and the search grid returned the
  user's **real photos** — content descriptions read *"Photo taken on Jun 12, 2023
  18:59"*, *"Photo taken on Jun 12, 2023 18:58"*, *"Photo taken on Nov 11, 2019
  12:59"* (all About-panels show `2.5 MP / 1080×2340` = the device screen
  resolution, i.e. screenshots).
- The **seeded** pizza files (`pizza1-5.jpg` in `DCIM/Camera`) are tiny
  **188–234-byte colored rectangles** (104×64…136×64 px, PNG bytes in a `.jpg`)
  that Google Photos' content search cannot recognize as pizza — so they never
  surfaced. The 4 **real** pizza JPGs in `/sdcard/Download/` weren't picked up by
  the "pizza" search either.
- The agent never verified the selected images were actually pizza; it only
  checked "resolution" (all identical 1080×2340) and assumed. The resulting
  *Best Pizza Photos* album contains **random user screenshots**.
- **Root cause:** defective seed data (placeholder rectangles instead of real
  pizza images) **and** no content verification by the model. This is the run's
  one confirmed false success — exactly what the user suspected.

## Failures

### 1. medium__gallery__001 — false pass (seed data + no content check)
See above. The album holds random screenshots, not pizza. The seed's "pizza
photos" were tiny colored placeholder rectangles that Google Photos search can't
match; the model picked whatever the search returned and trusted identical
resolutions over actual content. **Fix:** ship real pizza images as the seed and
instruct the agent to confirm a photo actually depicts the searched subject
before selecting it.

### 2. hard__calendar-telegram-obsidian__002 — Telegram Send-tap (device bug) + no ask_user
Obsidian note + meeting-details draft were done, but the Telegram **Send button
taps never registered** on the share sheet — the same flaky primitive seen in
prior runs. Also the agent never called ask_user for the attendee name (re-run
with qwen3.6-plus failed the same way: 150 steps, stuck in an `Expand`/`BACK` loop).

### 3. hard__chrome-telegram-notes__008 — (RESOLVED by qwen3.6-plus re-run)
The original run skipped the required "star the cheaper listing" step (agent got
stuck in the `system_button` newline bug and completed early). **The 2026-08-13
re-run fixed this:** it asked ask_user ("wireless earbuds"), compared prices
(Amazon ₹474 vs Flipkart ₹264), correctly sent no Telegram (under $10), and
**bookmarked** the listing → clean `complete`. Now a genuine PASS.

### 4. Device-capability honest failures (correct behavior)
- `easy__phone__001`: no per-unknown-number ringtone option exists on this build.
- `medium__camera__001`: no manual Night-mode/HDR toggles (flash-off was done).
- `easy__camera__001`: Gallery rename Save button unresponsive (device bug).

### 5. Data-precondition honest failures
- `medium__calendar__001`: no recurring no-attendee events exist today.
- `medium__obsidian__001`: no word-count surface in Obsidian mobile → step-exhausted loop.

## Recommendations

1. **Fix the pizza seed** (real pizza images) and add a "confirm the image actually
   shows X" step to gallery/search tasks — this run's only false pass.
2. **Telegram Send flakiness** — prefer share-sheet confirmation ("Share in 1 chat")
   which worked, and/or add delivery verification before declaring send success.
3. **`system_button` newline bug** — a `home\n`/`back\n` arg quirk made the model
   get stuck (hard__chrome-telegram-notes, and near-end of several tasks); normalize
   the arg so it can't loop.
4. **Interaction tasks that don't ask** — add a reminder in the system prompt that
   ASK USER tasks must call `ask_user` for the hidden fact even when a plausible
   default exists.
