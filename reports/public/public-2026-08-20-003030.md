## ⭐ Multi-turn (KB) deep dive — the headline finding

The public sample carries **4 multi-turn KB tasks** (`multiturn_kb_public.json`),
each graded on acting on the *correct target* resolved through dialogue with the
simulated user (gpt-5.4-mini), with rolling memory. Results: **2 pass, 1 false
pass (wrong target), 1 fail — and only 1 of 4 actually used the ask_user loop
correctly.**

| task_id | correct target | self-report | ask_user calls | verdict |
|---|---|---|---|---|
| hard__swiggy__005 | `swiggy::reorder-downtown-delight-murgh-mughlai` | success=True | 1 | ⚠️ **WRONG TARGET** — messaged the wrong contact and never reordered |
| hard__telegram-calendar__016 | `telegram::forever-21-date` | success=True | 0 | ✅ pass (found date in chat, created event) — but no user ask |
| hard__gmail-calendar__003 | `gmail-calendar::bbi-del-reminder` | success=False | 0 | ❌ FAIL — searched the wrong flight number, never asked |
| hard__music-obsidian__077 | `youtube-music::sleep-timer-1030pm` | success=False | 0 | ❌ FAIL — step-cap, never set the timer |

### hard__swiggy__005 — "reorder the food I ate in the past week" (WRONG TARGET)

The agent did engage the ask_user loop once — but the conversation **did not
converge on the right person**:

- Asked `"Who is 'him' that you want to message on Telegram?"` → oracle answered
  **"Yuvraj Singh Jio"**.
- It then searched Telegram for "Yuvraj Singh Jio" — **no exact match found** —
  and fell back to the **Yuvraj Airtel** chat, typing the order total there.
- The "order total" it found was **Rs. 160 → Maharani Restaurant** from SMS,
  whereas the correct target is reordering **Downtown Delight · Murgh Mughlai**
  (the "food I ate in the past week"). It **never reordered anything** — it just
  messaged a total to the wrong contact.

**Lesson:** the KB oracle resolved the ambiguous "him", but the agent's
contact-resolution logic (exact-match search → fallback to nearest "Yuvraj")
overrode the oracle. The correct target requires both the *reorder* action and
the *correct recipient*; only the message was sent. This is the clearest
multi-turn failure of the batch and should be a follow-up rerun focus.

### hard__telegram-calendar__016 — "date dropped in a chat → calendar" (PASS)

- The agent opened Telegram, found a chat with a date discussion
  ("Let's gather on 20th August…", "22nd of this month"), resolved the agreed
  date to **August 22**, and created a **"Meetup"** calendar event.
- **0 ask_user calls** — it resolved the date entirely from the UI rather than
  confirming with the user. For this task the KB profile (`forever-21-date`)
  expected dialogue; the GUI-only shortcut happened to land the right date, so it
  passes, but it exercised **no interaction** — worth noting the interaction
  path wasn't stressed.

### hard__gmail-calendar__003 — "next flight → calendar reminder" (FAIL)

- The KB profile's next trip is **IndiGo 6E 6893 · BBI→DEL · 2026-08-24 · 07:10**
  (with a past 6E 6737 as distractor).
- The agent searched Gmail for "flight confirmation", "IndiGo", and — critically —
  **"6E 6821"** (a *past* flight number, not the KB's next trip), found only old
  emails, and gave up. It **never asked the user which flight** (0 ask_user
  calls) and never created the reminder.
- **Lesson:** in the multi-turn flow the agent should disambiguate *which* flight
  via the KB oracle; instead it latched onto a stale flight number from its own
  context. The `ask_user` loop was available but unused.

### hard__music-obsidian__077 — "sleep timer at bedtime" (FAIL)

- The KB profile knows bedtime = **10:30 PM** (Obsidian `Bedtime.md`) and the
  habit (Chillhop lo-fi, low volume). The agent opened YouTube Music, clicked
  around (repeated `index 16/11` loops), and hit the **60-step cap** without
  ever setting a sleep timer. **0 ask_user calls**.
- **Lesson:** pure GUI navigation thrash in YT Music; the multi-turn oracle
  (which would confirm bedtime) was never consulted.

### Multi-turn takeaways

1. **Only 1 of 4 KB tasks actually used the ask_user loop** (swiggy — and it
   then ignored the answer's contact). The other three resolved (or failed)
   entirely GUI-side, so the multi-turn interaction mechanism was barely
   exercised.
2. **swiggy__005 is a silent wrong-target success** — the report counts it as a
   pass (self-reported success, 1 ask_user call), but it messaged the wrong
   contact and never performed the reorder. A strict KB-target check would mark
   it **FAIL**.
3. The multi-turn failure pattern is **not asking when the spec is ambiguous**
   (which flight, which date, which contact, what bedtime) — exactly the failure
   mode multi-turn tasks exist to catch.

## Failure analysis (non-multi-turn)

Of the 17 true failures, the causes cluster into:

- **Step-cap thrashes (60 steps, 8):** `easy__swiggy__001`, `hard__google-sheets-amazon-shopping__074`,
  `hard__google-search-telegram-clock__018` (alarm loop), `hard__photos-gmail-obsidian__012`
  (Obsidian stuck), `medium__google-drive__001/007`, `medium__files__009`.
- **App/UI limitations (4):** `medium__google-photos__008` (no duration filter),
  `medium__music-telegram__001` (YT Music no weekly stats), `easy__bookmyshow__004`
  (app "Request failed" 400), `easy__google-meet__004` (no meetings surfaced).
- **Under-specified task / agent gave up (2):** `medium__google-search__008`
  (no route given), `medium__contacts__012` (no dups + call incomplete).
- **ASK USER gate (2):** `hard__drive-notes-telegram__010` (guessed owner instead
  of asking), `hard__gmail-calendar__003` (never asked which flight).
